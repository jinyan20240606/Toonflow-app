# 段子执行协议设计

## 目标

以 [`Piplines/项目标准/00-小说段子原文.md`](../Piplines/项目标准/00-小说段子原文.md) 为输入源，设计一套**兼容项目现有分镜表格式**、并可**直接程序化解析进入分镜面板及后续生图/生视频流程**的执行协议。

本方案不再依赖现有短剧型导演规划与分镜表 Agent 进行二次导演化理解，而是将段子原文中的节拍、钩子、停顿与包袱结构，以可解析方式固化，并最终对齐项目数据库与前端数据结构。

## 核心结论

中间协议**不能另起一套完全脱离项目的 Beat/Item 新格式**。

正确方案应为：

### 分镜表兼容型执行协议

即：
- 主体格式继续使用现有分镜表 markdown 结构
- 在不破坏现有结构的前提下，新增少量可程序解析的节拍元信息
- 最终仍然能够直接映射到 `o_storyboard` 与 `flowData.storyboard`

换句话说：

**表面上它还是项目的分镜表，底层上它是段子节拍优先的可执行协议。**

## 协议结构设计

建议新增一份协议文件，例如：

- [`plan-docs/段子执行协议样例.md`](./段子执行协议样例.md)

该文件结构如下。

### 一、协议头

```md
<!-- protocol: storyboard-exec-v1 -->
<!-- source: joke-script -->
<!-- mode: comedy-clip -->
<!-- parse-target: storyboard -->
```

#### 含义

- `protocol`：协议版本号
- `source`：输入源类型
- `mode`：内容类型，当前为段子短视频
- `parse-target`：程序解析目标，固定为 `storyboard`

该层用于程序判断是否走“执行协议直转链路”。

---

### 二、场头

保持与现有分镜表一致：

```md
## 场1：网约车内·互怼攻防 ｜ 参演角色：女主、司机
```

#### 规则

- 必须保留场景名
- 参演角色必须按当前项目分镜表格式输出
- 参演角色名称需与资产名称匹配或可映射

---

### 三、片段头

保持与现有分镜表一致，并允许增加片段级 meta 注释：

```md
### 片段一（约3s）
<!-- storyboard-meta: {"beat":"hook","pace":"fast","mustKeepDuration":true,"maxExtendRatio":1.2,"shouldGenerateImage":true} -->
**引用资产名称**：[女主, 司机, 网约车内, 中控导航屏]
**引用资产ID**：[15, 16, 17, 18]
```

#### `storyboard-meta` 字段说明

- `beat`：节拍类型
  - 可选值：`hook` / `upgrade` / `rehook` / `punchline` / `ending`
- `pace`：节奏标签
  - 可选值：`fast` / `normal` / `pause` / `release`
- `mustKeepDuration`：是否强制保留片段时长约束
- `maxExtendRatio`：允许扩写的最大比例
- `shouldGenerateImage`：该片段镜头默认是否需要生图

#### 片段级资产规则

与当前项目分镜表保持一致：
- 资产名称、资产 ID 仍然是片段级
- 片段内所有镜头默认共用该片段资产集合
- 程序解析后写入每条 storyboard 时，继承当前片段的资产集合

---

### 四、镜表

镜表保持现有格式：

```md
| 序号 | 画面描述 | 时长 | 景别 | 运镜 | 台词 | 音效 |
|------|------|------|------|------|------|------|
| 1 | 网约车刚起步，副驾女主歪头盯着司机侧脸，眼神聚焦。 | 0.5 | 近景 | 固定 |  | 音效：车辆低频行驶声 |
| 2 | 女主突然伸手，直接挡住中控导航屏，动作干脆。 | 1.5 | 特写 | 固定 |  | 音效：手掌拍屏闷响 |
| 3 | 女主下巴微抬看向司机，得意立题；司机保持目视前方。 | 1 | 近景 | 固定 | 女主说：『别看了。你从上车导航没看几眼，全在看我。』 | 音效：导航提示声 |
```

#### 镜表字段约束

- `画面描述`：仍使用项目现有口径
- `时长`：必须为单镜最终执行时长，供程序直接写入 `o_storyboard.duration`
- `景别` / `运镜`：保留，供后续 `videoDesc` 与 `prompt` 拼接使用
- `台词`：原文一字不改
- `音效`：供 `videoDesc` 使用

---

### 五、可选镜头级 meta 注释

如某一镜头需要特别保留段子节拍约束，可在镜表前增加一行注释：

```md
<!-- shot-meta: {"shotNo":3,"pause":0.5,"role":"rehook","mustKeep":true} -->
```

#### 字段说明

- `shotNo`：对应镜头序号
- `pause`：明确停顿时长
- `role`：镜头功能，如 `rehook` / `reaction` / `punchline`
- `mustKeep`：是否必须强保

#### 使用建议

第一版只在以下场景使用：
- `卡住0.4秒/0.5秒`
- `re-hook`
- `终局 punchline`

这样既不会让协议过重，也能保留段子最关键的节拍点。

## 从 [`00-小说段子原文.md`](../Piplines/项目标准/00-小说段子原文.md) 到协议的映射规则

### 原文字段映射

| 原文来源 | 协议落点 |
|---|---|
| `### 第一拍/第二拍/第三拍` | `### 片段X（约Ns）` |
| `（1-3秒）/（10-15秒）/（5-8秒）` | 片段时长 + `storyboard-meta.mustKeepDuration` |
| `【首帧动作钩子】` | `storyboard-meta.beat=hook` 或镜头拆分依据 |
| `【re-hook】` | `storyboard-meta.beat=rehook` 或 `shot-meta.role=rehook` |
| `【终局视觉punchline】` | `storyboard-meta.beat=punchline` |
| `【女主媚笑卡住0.5秒】` | `shot-meta.pause=0.5` |
| `表演` / `镜头` 建议 | 拆分为镜表行 |
| 人物表 / 场景设定 / 道具 | 片段级引用资产 |
| 台词原文 | 镜表 `台词` 列 |

### 原则

- 先保留原文节拍
- 再转成项目分镜表结构
- 不允许先改成短剧式分镜，再回写节拍

## 程序解析到 storyboard 面板的映射规则

解析目标是 [`flowData.storyboard`](../src/agents/productionAgent/tools.ts:49) 与最终 [`o_storyboard`](../ai-docs/db-schema.md:227)。

### 一、片段级数据

#### 输入
- `场头`
- `引用资产名称`
- `引用资产ID`
- `storyboard-meta`

#### 输出到每条镜头
- 当前场景名
- 当前片段名
- 当前片段资产集合
- 当前片段节拍 meta

### 二、镜表行数据

#### 输入
- `画面描述`
- `时长`
- `景别`
- `运镜`
- `台词`
- `音效`
- `shot-meta`（可选）

#### 输出到 storyboard item

##### 1. `duration`
直接取镜表 `时长`。

##### 2. `associateAssetsIds`
直接继承当前片段的 `引用资产ID`。

##### 3. `track`
直接按镜头顺序全局递增：
- 第一条镜头 `track="1"`
- 第二条镜头 `track="2"`
- 以此类推

该策略兼容当前前端及 [`o_storyboard.track`](../ai-docs/db-schema.md:239)。

##### 4. `shouldGenerateImage`
优先取：
- 当前镜头 `shot-meta` 指定值
- 否则取当前片段 `storyboard-meta.shouldGenerateImage`
- 默认 `true`

写入时转换为项目当前值：
- 面板层：`"true" / "false"`
- 数据库层：`1 / 0`

##### 5. `videoDesc`
由程序按固定模板拼接：

```text
场景：{场景名}
片段：{片段名}
节拍：{beat}
画面描述：{画面描述}
景别：{景别}
运镜：{运镜}
台词：{台词}
音效：{音效}
引用资产名称：{片段资产名称}
引用资产ID：{片段资产ID}
```

说明：
- `videoDesc` 不需要完全复刻 markdown
- 但必须包含当前前端编辑与视频生成所需信息
- 必须与项目字段口径一致

##### 6. `prompt`
第一版建议走程序模板生成：

拼接来源：
- 场景名
- 画面描述
- 景别
- 运镜
- 台词（可选）
- 资产名称

第一版目标不是极致 prompt，而是先打通稳定链路。

## 与数据库表更全面的对齐说明

### 1. [`o_storyboard`](../ai-docs/db-schema.md:227)

| 字段 | 来源 |
|---|---|
| `scriptId` | 当前剧本 ID |
| `projectId` | 当前项目 ID |
| `prompt` | 程序模板生成 |
| `videoDesc` | 程序固定模板拼接 |
| `duration` | 镜表 `时长` |
| `state` | 初始为 `未生成` |
| `track` | 全局顺序号 |
| `shouldGenerateImage` | 片段/镜头 meta |
| `index` | 镜头顺序 |
| `reason` | 初始空 |
| `createTime` | 后端落库生成 |

### 2. [`o_assets2Storyboard`](../ai-docs/db-schema.md:248)

| 字段 | 来源 |
|---|---|
| `storyboardId` | 分镜落库后生成 |
| `assetId` | 当前片段的 `引用资产ID` |

### 3. [`o_agentWorkData`](../ai-docs/db-schema.md:292)

新链路仍建议保留：
- `flowData.storyboardTable`：保存协议文本
- `flowData.storyboard`：保存解析后的面板数据

这样既兼容前端当前工作流，也方便回放与调试。

### 第三阶段
复用现有能力：
- [`add_flowData_storyboard()`](../src/agents/productionAgent/tools.ts:243)

- 后续视频轨道流程

## 最终结论

本执行协议的核心不是发明新系统，而是：

- 继续使用项目现有的分镜表主格式
- 通过 `storyboard-meta` / `shot-meta` 增强段子节拍约束
- 程序直接解析成项目现有的 storyboard 面板与数据库结构
- 绕开短剧型导演规划与分镜表 Agent

一句话总结：

**这套协议是“项目现有分镜表格式的段子执行增强版”，目标是让 [`00-小说段子原文.md`](../Piplines/项目标准/00-小说段子原文.md) 能稳定、保真、可程序落库地进入 [`o_storyboard`](../ai-docs/db-schema.md:227) 和后续生图/生视频流程。**
